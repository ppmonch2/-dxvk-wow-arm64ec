# Проверка WOW-CUSTOM-ARM64EC в WeHavePhones

## Назначение
Диагностическая сборка upstream DXVK v2.3.1 для ARM64EC.
Цель — доказать загрузку собственных d3d11.dll И dxgi.dll в 64-битном DX11-клиенте WoW Forever.
Производительность не оптимизирована. GPLAsync-патчи не добавлены.
Совместимость с конкретным Wine/WeHavePhones на планшете требует проверки.
ARM64EC не подходит для 32-битного WoW.

## Безопасный тест
1. Создайте отдельный тестовый контейнер, по возможности клонируя настройки рабочего.
   Игра и её настройки тоже должны находиться в отдельной копии: общий каталог игры меняет оба контейнера.
   Не заменяйте DLL рабочего контейнера, не очищайте его кеши.
2. Полностью завершите процессы игры в тестовом контейнере.
3. Распакуйте ZIP-артефакт GitHub Actions. Сверьте d3d11.dll и dxgi.dll с SHA256SUMS,
   если в среде доступен sha256sum. Сохраните BUILD-INFO.txt.
4. Скопируйте ОБЕ DLL рядом с фактически запускаемым 64-битным EXE игры,
   не рядом с лаунчером, если игра запускается из другой папки. Старые локальные DLL сохраните отдельно.
5. В параметрах окружения запуска игры тестового контейнера задайте:
   WINEDLLOVERRIDES=d3d11,dxgi=n
   DXVK_HUD=version,api,fps
   DXVK_LOG_LEVEL=info
   DXVK_LOG_PATH=.
   WINEDEBUG=+loaddll
   Если WINEDLLOVERRIDES уже задан, объедините записи через точку с запятой,
   удалив конфликтующие записи для d3d11/dxgi. Значение n означает native-only:
   отсутствие совместимой DLL должно дать ошибку, а не незаметный откат на builtin.
6. DXVK_LOG_PATH=. означает текущую рабочую папку процесса, которая может отличаться от папки EXE.
   Предпочтительно заранее создать отдельную доступную для записи папку в тестовом контейнере
   и указать в DXVK_LOG_PATH её абсолютный путь, доступный Wine.
   Значение none отключает файлы. Логи DXVK при Wine могут иначе уходить только в консоль.
7. Выберите DirectX 11 штатным способом этого клиента. Для клиентов с поддержкой такого параметра
   можно использовать -d3d11. Запускайте тот же EXE и тем же способом, что обычно.
   Если WeHavePhones при запуске перезаписывает DLL или overrides, отключите автоматическую
   установку встроенного DXVK только в тестовом контейнере либо используйте его механизм custom DXVK.
   Точные названия пунктов меню зависят от версии приложения.
8. На экране найдите строку:
   DXVK v2.3.1... | WOW-CUSTOM-ARM64EC [<12 символов коммита>]
9. В СВЕЖИХ логах <имя_EXE>_d3d11.log и <имя_EXE>_dxgi.log должны быть соответственно:
   WOW-CUSTOM-ARM64EC build=<commit> module=d3d11.dll D3D11InternalCreateDeviceAndSwapChain
   WOW-CUSTOM-ARM64EC build=<commit> module=dxgi.dll createDxgiFactory
   Идентификатор build должен совпадать с первыми 12 символами Repository commit в BUILD-INFO.txt.
   Строка DXVK instance initialized — дополнительная диагностика.
10. Сохраните скриншот HUD, оба свежих лога и вывод Wine +loaddll с путями загруженных модулей.
    После проверки отключите +loaddll: избыточное логирование мешает измерению производительности.

## Как оценить результат
- HUD с меткой подтверждает выполнение нашего кода HUD.
- Обе module= строки с нужным build и путями из +loaddll подтверждают использование пары DLL.
- Одна module= строка означает, что загрузка обеих наших DLL ещё не доказана.
- Версия 2.3.1 без метки, наличие файлов в папке или метка внутри ZIP не доказывают загрузку.
- Нет логов: проверьте путь, права записи, фактический EXE, overrides и перезапись DLL при старте.
- Игра не запускается с native-only: сохраните лог Wine. Возможны неподходящая разрядность,
  отсутствие поддержки ARM64EC в Wine или несовместимость библиотек. Не переносите эксперимент в рабочий контейнер.
- Это не проверка FPS и не доказательство устранения фризов. Лимит 45 FPS и остальные настройки пока сохраните.

## Откат
Закройте тестовую игру, верните сохранённые DLL и настройки окружения в тестовой копии
или удалите тестовый контейнер вместе с отдельной копией игры.
