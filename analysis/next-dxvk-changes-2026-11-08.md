# Следующие изменения DXVK для WoW Forever / Adreno 650

Дата: 2026-11-08. Это результат анализа и план реализации, не новая сборка DLL.
Приложение WeHavePhones, main и рабочий контейнер в ходе этого анализа не менялись.

## Рекомендация

Первый кандидат — перенести в нашу native ARM64 DXVK 2.3.1 управление отправкой команд,
учитывающее тайловую архитектуру Adreno. Начать с эвристики отправки и границ render pass;
оптимизацию сохранения отброшенных render target вынести в отдельный следующий эксперимент.
Не объединять это с прежней принудительной ранней отправкой readback: действия могут
конфликтовать по частоте отправок и стоимости выгрузки тайлов в память.

Второй кандидат для сравнения — отдельная native ARM64 сборка DXVK 2.7.1 без наших
экспериментальных изменений: она уже содержит согласованный набор этих upstream-изменений.
DXVK 3.1.1 — актуальный стабильный релиз на момент проверки, но у него больше обязательных
Vulkan-функций и расширений. Совместимость через Android wrapper пока не доказана ни для
новой 2.7.1, ни для 3.1.1; это проверяется отдельно. Обе версии запрашивают Vulkan 1.3.

## Что действительно известно

- Пользователь запустил WoW с нашим Proton 11; заметного прироста относительно предыдущего
  runtime нет. Это результат этого теста, а не доказательство отсутствия всех накладных расходов Wine.
- В прежнем WAIT-журнале за 60.350811 с: 533 Map-вызова, суммарно 26.247596 с;
  вложенные ожидания ресурса — 25.722391 с, в среднем 48.2596 мс; CS-синхронизация — 0.522329 с.
  Максимум одного ожидания ресурса — 95.478 мс. Суммарные блокировки DXGI window/buffer
  во всём журнале — 47 + 48 микросекунд.
- Map включает вложенное ожидание ресурса: эти времена нельзя складывать. Это CPU-длительности
  вызовов; они не равны чистому GPU-времени и не устанавливают процент времени кадра.
- Старый WAIT не записывал MapType/Usage/размер ресурса. Он не доказывает, что все эти ожидания
  относятся к чтению GPU→CPU: в DXVK 2.3.1 тот же WaitForResource используется при записи.
- В прежнем LAB были длительные рывки и при остановившемся счётчике фоновой компиляции.
  Поэтому повторять только изменения async/compiler workers недостаточно; синхронная
  компиляция этими данными полностью не исключена.

## Кандидаты по коду

| Приоритет | Изменение | Почему подходит | Ограничение |
|---|---|---|---|
| 1 | Отправки команд с учётом тайлов и границ render pass | Adreno — тайловый GPU. Частые отправки посреди проходов могут увеличивать стоимость выгрузки/восстановления render target | Требуется адаптация нескольких участков 2.3.1, не простой cherry-pick |
| 2 | Пропуск сохранения render target, явно отброшенного игрой | Снижает лишние записи изображения в память | Применять DONT_CARE только при доказанном покрытии нужных подресурсов; не отбрасывать нужные игре данные |
| 3 | Исправление памяти CPU-читаемых напрямую отображаемых текстур | Небольшой upstream-патч применим к 2.3.1 | STAGING уже запрашивает HOST_CACHED; без данных о ресурсах эффект для WoW неизвестен |
| Условно | Предпочтение cached coherent memory для CPU-доступных аллокаций | В upstream отдельно отмечена медленная некэшируемая запись на ARM | Нужен реально доступный подходящий тип памяти от драйвера/ядра; перенос общего аллокатора значительно сложнее |
| Контроль | Целиком native ARM64 DXVK 2.7.1 | Содержит новую синхронизацию и tiler-изменения в согласованной базе | Больше изменений одновременно; сначала проверка возможностей Vulkan wrapper |

### 1. Эвристика отправки для тайловых GPU

- [80fb7e2294768e47af1a84ccd47d93dfbed839bb](https://github.com/doitsujin/dxvk/commit/80fb7e2294768e47af1a84ccd47d93dfbed839bb), впервые в 2.6:
  уменьшает активность эвристики отправки на тайловых GPU.
- [a145634438fef9ec99878fa5ebdf0a79d8f4754f](https://github.com/doitsujin/dxvk/commit/a145634438fef9ec99878fa5ebdf0a79d8f4754f), впервые в 2.7:
  переносит отложенную необходимую отправку на границу render pass, чтобы одновременно
  избегать излишних отправок внутри проходов и задержек чтения.
- В 2.7.1 выбор tiler mode явно включает VK_DRIVER_ID_MESA_TURNIP и Qualcomm.
  В нашей 2.3.1 соответствующей эвристики и preferRenderPassOps ещё нет.

Проект первого переноса: отдельный переключаемый путь только для подтверждённого Adreno/
Turnip; регистрация реального driverID и принятого режима; сохранение ExplicitFlush,
синхронизации Map и event/fence. При непрозрачном wrapper нельзя полагаться только на
строку GPU «740»: физический GPU планшета — Adreno 650.

Не переносить для первого теста [c276b56bb84b78b7e46493e82fd5837c16c690f5](https://github.com/doitsujin/dxvk/commit/c276b56bb84b78b7e46493e82fd5837c16c690f5):
это обход проблем Unity с подавлением некоторых explicit Flush, и автор отдельно отмечает
возможность deadlock. Это иной механизм, а его применимость к WoW не установлена.

### 2. Отброшенные render target

[fcabffc1e54e073967b635afdc2554c2bb5e03ee](https://github.com/doitsujin/dxvk/commit/fcabffc1e54e073967b635afdc2554c2bb5e03ee), впервые в 2.6,
добавляет store-op оптимизацию при discard изображения в tiler mode. Нужна отдельная
адаптация к структурам render pass в 2.3.1 и отдельный визуальный тест. Выгода зависит
от того, использует ли WoW подходящие discard-вызовы.

### 3. Выбор памяти

[35d94ae0575a6effccd5a62df879824aee34d5b8](https://github.com/doitsujin/dxvk/commit/35d94ae0575a6effccd5a62df879824aee34d5b8), впервые в 2.5,
учитывает CPU_ACCESS_READ при выборе HOST_CACHED для напрямую отображаемых текстур.
Сухая проверка git apply --check на чистой 2.3.1 успешна. Это не проверка компиляции или FPS.

[e3d3f69fe3707a6c0b6886262d404f5af92b4b33](https://github.com/doitsujin/dxvk/commit/e3d3f69fe3707a6c0b6886262d404f5af92b4b33), впервые в 3.0,
предпочитает cached memory для mapped-аллокаций на тайловых GPU. Аллокатор новой DXVK
существенно отличается от 2.3.1; прямо этот патч не применяется.

В исходниках Mesa на ревизии, указанной в комплекте WeHavePhones (`1b51639c20`):
- `tu_device.cc`: тип 0 — DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT;
- дополнительный HOST_CACHED | HOST_COHERENT тип появляется только при
  has_cached_coherent_memory;
- `tu_knl_kgsl.cc`: KGSL проверяется реальной аллокацией с IOCOHERENT + WRITEBACK и
  проверкой фактически возвращённых флагов. Ядро может молча снять неподдерживаемый флаг.

Поэтому нельзя «ускорить» драйвер простым объявлением cached coherent там, где этого
не поддерживает ядро/GPU. Нужен фактический список memoryTypes от работающего wrapper.
Проверенные исходники Mesa не доказывают полного соответствия бинарному драйверу:
в manifest WeHavePhones исходные build flags и первоначальный издатель бинарника не записаны.

## Почему новая DXVK требует отдельной проверки

Контрольные ревизии: 2.3.1 — 037d0fa1ad093065b18dad968d5898cbcd143e0e;
2.7.1 — c3dd74be6baec53786d4e064a572185b70347a17;
3.1.1 — b1a1c99ab52b687cf950d62c88bc2fa316b41663.

В профиле требований 2.7.1 есть maintenance5 и descriptor-indexing функции;
в 3.1.1 добавляются, в частности, обязательные maintenance6 и load_store_op_none.
В старом журнале maintenance5 включён. Полного списка доступных свойств/функций wrapper
в нём нет. Нули у bufferDeviceAddress и ряда других функций НЕ доказывают их отсутствия:
код 2.3.1 печатает enabledFeatures, а не полный набор доступных возможностей устройства.

Обновление 2.3.1→2.7.1 также меняет CPU/GPU-синхронизацию (например,
[27539fc83847c74e619307c606309234d8a3b2e0](https://github.com/doitsujin/dxvk/commit/27539fc83847c74e619307c606309234d8a3b2e0), timeline semaphores),
а не только номер версии. Нельзя приписать результат полного обновления одному патчу.

## Проверенный объём работы и следующий шаг

Выполнены чтение кода, истории upstream и старых журналов, сопоставление требований
Vulkan и пять сухих проверок переноса. Четыре выбранных больших изменения напрямую
к 2.3.1 не применяются; патч 35d94ae0 применяется. Результаты — в соседнем JSON.
Исходники DLL, драйвера и приложения не правились; новые DLL и APK не собирались.

Далее, после выбора идеи: реализовать только tiler-aware отправку в отдельной DXVK-ветке;
собрать native ARM64 DLL; проверить выключенный/включённый путь с одинаковым остальным
кодом. Критерий результата — время кадров и рывки на одном маршруте после прогрева,
плюс изменение Map/resource ожиданий. Прирост FPS и уменьшение рывков заранее не обещаются.
